# AGENTS.md

Single-application **Angular 21** project using the modern standalone style: no NgModules, signal-based components, `provideHttpClient`/`provideRouter`. **Client-side only — SSR is disabled** (no `@angular/ssr`, no server entrypoints; `angular.json` builds browser output only). Root is this directory (`Veimen Web/`); the git repo root is the parent (`../`).

## Commands

```bash
npm start            # dev server on http://localhost:4200
npm run build        # production build; output in dist/veimen-web/browser
npm test             # unit tests (watch mode)
npx prettier --write .   # formatting
```

- `npm test` maps to `ng test` using the `@angular/build:unit-test` builder (Vitest-based). It runs in **watch mode**; use `npx ng test --watch=false` for a single run.
- No lint or typecheck script exists; the strict TS config is the type gate. Run `npx ng build` to type-check the app (strictTemplates is on) before relying on tests alone.
- Package manager is npm (pin `packageManager: npm@11`). Node 20.19+/22+ required for Angular 21.

## Architecture

- Entrypoint: `src/main.ts` (browser bootstrap via `bootstrapApplication`). There is no server entrypoint.
- Routes in `src/app/app.routes.ts`. All rendering happens client-side.
- `src/app/` layout: feature folders (e.g. `dashboard/` hold `*.ts`, `*.html`, `*.css`, `*.spec.ts` together) plus `services/`.
- Features: a dashboard (`DashboardComponent`), a token-usage dashboard (`TokensDashboardComponent`) and a requests list (`ServiceRequestComponent`) that fetch data via `DashboardService`/`TokensService`/`RequestsService` and render ngx-charts. All services build their URLs from `environment.apiBaseUrl` (same pattern as `AuthService`): `${apiBaseUrl}/api/ServiceRequests/dashboard`, `${apiBaseUrl}/api/ServiceRequests/tokens`, `${apiBaseUrl}/api/ServiceRequests` and `${apiBaseUrl}/api/ServiceRequests/trace`. Because those URLs start with `apiBaseUrl`, requests go through `authInterceptor` (Bearer token + 401 refresh/redirect). **Estas tres pantallas filtran por el cliente elegido en el filtro global del menú** (`ClientContextService`): envían `client_id = selectedClient()?.clientId` (las tres APIs lo aceptan; ausente = sin filtro por cliente) y recargan el rango actual cuando cambia la selección (un `effect` sobre `selectedClient`, con el primer disparo descartado porque la carga inicial ya la hace `ngOnInit`).
- **Token usage dashboard** (`/tokens`, feature folder `tokens/`): consumes `GET /api/ServiceRequests/tokens` (permission `tokens.read`, backend RBAC). The endpoint returns a flat list of `{ date, node, llmModel, inputTokens, outputTokens, totalTokens }` already aggregated by day × node × llm_model, and **only for `node_type = 'LLM'`**. Date filtering uses the `yyyyMMdd` format on both sides (`TokensService.toApiDate`), and the range applies to the trace's `end_date`, not to the request's creation date. `llmModel` is kept in the frontend `TokenUsage` model (empty string when the trace did not record a model) and feeds the "Tokens por modelo" bar chart and the detail table. Because the API separates rows by model, `TokensDashboardComponent.modelDetail()` re-aggregates them by model across the whole range (summing `inputTokens`/`outputTokens`/`totalTokens`; traces without a model fall under `—`), and `byModel()` is derived from it. `totalTokens` is summed from each row's own `totalTokens` (matching the backend's `SUM(total_tokens)`), never derived as `input + output`. The view shows 4 KPI cards, a daily line chart (input vs output), a horizontal bar chart by model, a horizontal bar chart by node, and a detail table **by model** (Modelo/Input/Output/Total plus a totals footer) capped at 50 rows with a "Ver más" button. No hay filtros propios de la pantalla (ni persistencia en `localStorage`): lo único que acota los datos aparte del rango de fechas es el **filtro global de cliente** (`client_id`, ver la viñeta del filtro global). Además de los KPIs de tokens, la pantalla muestra **dos cards de costo** («Promedio diario de consumo en US$» y «Monto acumulado en el mes en US$»; el rótulo de moneda lo resuelve `costCurrencyLabel()`, USD → "US$") alimentadas por `GET /api/usage/costs` —el endpoint de Uso OpenAI— **con la misma lógica de ese componente**: el request va en `forkJoin` con el de tokens (error por fuente: si fallan los costos solo aparece el `.warning` de `costError` y las cards se ocultan, los tokens siguen cargando), se arma con el rango seleccionado (`start_date` es obligatorio: sin «Desde» no se dispara y `of(null)` limpia las filas de costo) y con `project_ids` del cliente global (`projectIds`, análogo a `client_id` en los tokens), y los importes se agregan **solo sobre la moneda principal** (`currencyTotals`/`primaryCurrency`/`rowsInPrimaryCurrency`, nunca se suman entre monedas; `avgPerDay` = importe / días con costo, con aviso `.notice` si hay más de una moneda). El endpoint exige `usage.read` (RBAC): sin ese permiso no se pide nada (`canReadUsage`) y las cards quedan ocultas en vez de exponer un 403 permanente.
- **Uso OpenAI** (`/uso-openai`, feature folder `usage/`, stylesheet `usage/usage-dashboard.css`): pantalla unificada que reemplaza a las antiguas `/consumo` y `/costos` (ambas siguen existiendo como `redirectTo: 'uso-openai'`). Consume en paralelo los dos endpoints del backend `UsageController` (permiso **`usage.read`**, i.e. `PERMISSIONS.usageRead`) con `forkJoin`, y reutiliza el UX de filtros de fecha del dashboard de tokens (Desde/Hasta + botones filtrar/recargar, rango por defecto de 30 días, conversión `yyyyMMdd` vía `UsageService.toApiDate`).
  - Si **una** de las dos fuentes falla, la otra se sigue mostrando (`usageError`/`costError` por separado + banners `.warning`); solo cuando fallan las dos se muestra el error con "Reintentar" (`allFailed`).
  - Como en ningún otro endpoint, **`start_date` es obligatorio aquí** (la API de OpenAI exige `start_time`; `UsageController.ValidateDates` devuelve 400 si falta); por eso `UsageService` usa un `UsageDateRange` con `startDate` requerido y el componente no dispara peticiones si se limpia la fecha.
  - `GET /api/usage/completions`. El envelope de OpenAI llega en **snake_case**: `{ object, data: [{ start_time, end_time, results: [...] }], has_more, next_page }`. `UsageService.flatten()` colapsa `page → bucket → results` a una fila por bucket × result. `start_time`/`end_time` son **epoch en segundos** y los buckets son `bucket_width=1d` desde medianoche UTC, así que el día se lee con `toISOString()` (con getters locales el día se corre en zonas negativas). `totalTokens` **se** deriva como `input + output` (al revés que el dashboard de tokens) porque `input_tokens`/`output_tokens` ya incluyen `input_cached_tokens`/`input_audio_tokens` (van como columnas aparte, nunca se suman). OpenAI devuelve una fila por día × modelo × proyecto × api_key × user, así que `modelDetail()` re-agrega por modelo en todo el rango (modelo ausente → `—`).
  - `GET /api/usage/costs`. Mismo envelope; el importe vive en `amount.value` y la moneda en `amount.currency`. **Los importes nunca se suman entre monedas**: `currencyTotals()` las rankea, `primaryCurrency()` es la mayor (desempate alfabético) y es la única que se grafica/totaliza, mientras `otherCurrencies()` alimenta un aviso con el resto. `lineItemDetail()` agrupa por `line_item`, y `quantity` se muestra **solo cuando todas las filas del concepto comparten unidad** (pasa a `null` → `—` cuando mezcla tokens/requests/etc., porque sumarlos es engañoso).
  - El **agrupamiento del backend es por `project_id`** (no por `api_key_id`), combinado con `model`/`line_item`; por eso `CompletionUsage`/`CostEntry` exponen `projectId` (`''` → `—`) y hay desglose por proyecto.
  - El backend ya recorre todas las páginas de OpenAI (`UsageService.GetAllPagesAsync`), así que `has_more`/`next_page` siempre vienen vacíos: **no hay paginación cliente-side**.
  - **Filtro por cliente/proyecto**: ya **no hay selector interno**; el componente consume el **filtro global de cliente** de la cabecera del menú (`ClientContextService.selectedClient`, ver la viñeta del filtro global). El `projectId` del cliente elegido se envía como `project_ids` (un único valor) a **ambos** endpoints vía `UsageService.toParams`; «Todos» (`null`) y un cliente sin `projectId` no envían el parámetro. Al cambiar el cliente en el menú el componente **recarga** solo el rango actual (un `effect` sobre `selectedClient`; el `requestId` descarta las respuestas de selecciones anteriores). El componente ya no pide `GET /api/clients` (lo carga el menú), así que los desgloses por proyecto (los gráficos "Tokens por proyecto" y "Costo por proyecto", y la tabla "Detalle por proyecto") rotulan con el **nombre del cliente**: el backend agrega `project_name` a cada resultado (`CompletionUsage.projectName`/`CostEntry.projectName`) y `projectLabel()` lo usa primero; si no viene, cae al mapa `projectId`→`name` de `ClientContextService.clients()` (incluyendo inactivos) y, si tampoco hay coincidencia, al `projectId`.
  - Vista: dos `.stats-row` (KPIs de consumo y KPIs de costo en la moneda principal), evolución diaria de consumo (entrada vs salida, leyenda HTML), evolución diaria de costo, barras de tokens y de costo **por proyecto**, barras por modelo, barras por `num_model_requests` y por concepto; y tablas de detalle **diario** (una fila por día con consumo + su costo total, ordenada por fecha desc; los días solo-con-costo no aparecen), **por proyecto** (unión de proyectos con consumo o costo, ordenada por tokens desc; incluye proyectos que solo tienen costo, p. ej. imágenes, con 0 tokens), **por modelo** y **por concepto** (cada una con tope de 50 filas + "Ver más").
- `GET /api/ServiceRequests` is **paginated**: it accepts `page`/`pageSize` query params and returns `{ items, totalCount, page, pageSize }` (ASP.NET `PagedResult<T>`, **camelCase** JSON — the API serializes `ServiceRequest` properties in camelCase). It does **not** return `totalPages`; `RequestsService` computes it as `ceil(totalCount / pageSize)`. `ServiceRequestComponent` keeps `page`/`totalPages`/`totalCount` signals, requests the current page, and resets to page 1 when filters change. También envía `client_id` con el **filtro global de cliente** (`RequestsService` lo omite cuando no hay cliente elegido) y, al cambiar la selección, vuelve a la página 1 y recarga (el conjunto de resultados cambia).
- **Auditoría de requerimientos**: el botón "Informe de auditoría" (en la lista y en el modal de `ServiceRequestComponent`) llama a `RequestsService.auditRequest()`, que hace `POST ${apiBaseUrl}/api/ServiceRequests/audit?request_number=…`. La URL del webhook de n8n **ya no vive en el frontend** (se eliminó `auditWebhookUrl` de `environment.ts`/`environment.development.ts`): el backend llama a n8n y toma el email del usuario del token. Al empezar con `apiBaseUrl`, la petición pasa por `authInterceptor` (Bearer + 401).
- **Request trace order**: `ServiceRequestComponent.loadTrace()` sorts the steps by `traceId` (`[...steps].sort((a, b) => a.traceId - b.traceId)`), matching the backend's `ORDER BY trace_id`. Do **not** sort by `sequence`: it's the logical step order within the flow and can repeat across runs, so it desyncs from the real insertion order.
- **Trace input/output (JSON)**: the "Ver entrada / salida (JSON)" button expands the payload **inline** inside the step card (`expandedJsonSteps`, a `Set<traceId>` toggled by `toggleJson()`, rendered by `isJsonExpanded()`); it must **not** open a new tab. It used to build an HTML document and call `window.open()` — that was removed. Two `<pre>` panes (Entrada/Salida) show `formatJson()` output; Angular interpolation escapes it, so no manual `escapeHtml` is needed. The expanded set is cleared in `openDetail()`/`closeDetail()`.
- **Prompts module** (`/prompts`, feature folder `prompts/`): the list (`PromptsListComponent`) and the editor (`PromptFormComponent`) talk to the backend `PromptsController` — `GET /api/prompts`, `GET /api/prompts/{id}`, `POST /api/prompts` (201 + body), `PUT /api/prompts/{id}` (204) and `DELETE /api/prompts/{id}` (204, **borrado lógico**: el backend marca `deleted = 1`), permissions `prompts.read`/`prompts.write`. The list has an **Eliminar** button (native `confirm` → `DELETE` → the row is removed locally) next to Editar, shown only with `prompts.write`. Because those URLs start with `environment.apiBaseUrl` they go through `authInterceptor` (Bearer + 401 refresh); the old n8n webhooks (`prompts-list`/`prompt-detail`, snake_case) were removed — `PromptsService.normalizePrompt()` maps the API's nullable camelCase payload onto the non-nullable `Prompt` interface the rest of the app uses. The `prompt` table has **no `agent` column** (the agent's name lives in `agent_group`), so `agent` was removed from the API model/repository and from the web form/list; `schemaOutput` **is** a real column (after `updated_at`) and stays. Saving is done by the form's submit button (`(ngSubmit)="save()"`), disabled while `form.invalid || isSaving() || isLoading()`; on success it navigates back to `/prompts` (the list reloads in `ngOnInit`), on failure the error stays inline in `saveError()` and the form remains open. Contract details that bite: `agentGroup` is `[Required]` in the API model (empty → 400), `maxTokens` is nullable (`null` = sin límite; the control defaults to `null` and `Validators.min(1)` only rejects values `< 1`, so a `0` default would leave the form permanently invalid), `created_by`/`updated_by` are **not** filled by the backend (only `created_at`/`updated_at`) so the component sends `AuthService.currentUser().username`, and `createdAt`/`updatedAt` must go as ISO 8601 (`'YYYY-MM-DD HH:mm:ss'` → `T`, empty → `null`) because System.Text.Json rejects the space format. The list remembers the last **search text** across navigation in `localStorage` (`veimen-web.prompts.searchText`), hydrated in the signal initializer so returning to `/prompts` shows the query and filters the table by it (reset via "Limpiar filtros" clears the stored value). The editor has a **Clonar** button, shown only while editing (`id > 0`), that leaves the id at `0` and clears the audit fields so the next save goes through `POST` (inserts a new prompt).
- Styling is **Tailwind CSS v4** (imported in `src/styles.css`); charts/templates in components use their own scoped CSS files.
- **Design system tokens** (defined in `:root` in `src/styles.css`): everything derives from the Veimen navy + teal brand, never from neutral greys. Surfaces: `--vm-abyss`/`--vm-deep` (dark: sidebar, login, JSON panes), `--vm-paper` (`#eef3f7`, cool tint of the navy) for the content background, `--vm-surface` for cards, `--vm-wash` for subtle fills. Text: `--vm-ink`/`--vm-muted`/`--vm-faint`. Lines: `--vm-line`/`--vm-line-strong`. Accents on light: `--vm-teal-ink` (`#0c7d6d`, AA-safe teal for text), `--vm-teal-wash`, `--vm-teal-line`, `--vm-blue`/`--vm-blue-ink`/`--vm-blue-wash`. Semantics: `--vm-danger*`, `--vm-warn*`. The old `--veimen-*` names remain as aliases (sidebar/login used them) and resolve to the new tokens. Rules: **teal is scarce** (active nav rail, primary buttons, focus, brand mark) and **blue is the interactive/info accent** (links, spinners, focus rings on inputs, status badges); **hairlines instead of shadows** (drop shadows only for real elevation: dropdown, modal, toast); radius hierarchy is cards `0.625rem` / controls `0.375rem` / pills `9999px`. Typography: **IBM Plex Sans** for UI and **IBM Plex Mono** (`--vm-mono`) for data only — KPI values, table numerals/dates, prompt codes/versions, service-request numbers/dates, JSON payloads. Loaded via Google Fonts in `src/index.html`. No ALL-CAPS tracked-out labels: nav group titles, table headers, `dt`s and pane headers are sentence case.
- **Chart palettes** are brand-derived (teal `#2bb8a3`, blue `#3d7dd8`, amber `#d99a2b`, coral `#d95f5a`, violet `#8b7bc7`, …), not the ngx-charts/Material default: `dashboard.component.ts` maps the five status hues positionally (info/error/ok/warn/other), while `tokens-dashboard.component.ts` and `uso-openai.component.ts` share the same 10-colour `BASE_PALETTE` ramp (so a model keeps its colour across screens); the input/output line series are blue vs teal.
- **Permissions (backend RBAC)**: `services/permissions.service.ts` holds signal state (`profile`/`permissions`/`loaded`) plus the `PERMISSIONS` code map, which mirrors the backend's `Services/Permissions.cs` (`prompts.read`, `prompts.write`, `service-requests.read`, `trace.read`, `dashboard.read`, `tokens.read`, `usage.read`, `users.manage`, `businessModel.read`, `clients.read`, `clients.write`). Source: `GET /api/auth/me/permissions` (reads JWT claims). `AuthService` reloads permissions after `login()`/`refresh()` and in `initialize()`, and clears them in `clearSession()` — they live in memory only, never in localStorage.
- Routes are gated with `permissionGuard(...codes)` from `auth/permission.guard.ts` (denied → `/sin-acceso`, `AccessDeniedComponent`); the empty child route renders `shell/home-redirect.component.ts`, which navigates to the first accessible module via the pure helper `firstAccessiblePath()` (sidebar order, fallback `cambiar-contrasena`). A guard-only route is not possible (Angular NG04014 requires component/redirectTo/children). Post-login/register navigation defaults to `/` so users land on their first permitted module. In templates, `*appHasPermission="PERMISSIONS.xxx"` (`auth/has-permission.directive.ts`) hides elements (shell nav, prompt create/edit buttons). This is **UX only** — the API enforces the same permissions via policies (403).
- **Sidebar** (`shell/shell.html`) groups its nav into `Monitorear` (Dashboard, Uso OpenAI, Consumo de tokens, Requerimientos) and `Administrar` (Clientes, Usuarios, Prompts), with `Modelo de negocios` as an ungrouped item below. Each permission-gated link keeps its own `*appHasPermission`; the `Monitorear` category is hidden when the user has none of its permissions (`ShellComponent.canMonitor`), and `Administrar` is hidden when the user has none of its permissions (`ShellComponent.canManage`: `clientsRead`, `usersManage` o `promptsRead`). `Administrar` follows the order Clientes → Usuarios → Prompts. La **cabecera del sidebar** ya no muestra el logo «Veimen»: la ocupa el filtro global de cliente (ver abajo); el de la topbar móvil se mantiene.
- **Filtro global de cliente** (`services/client-context.service.ts` + cabecera del sidebar): el menú reemplaza el logo «Veimen» por un contexto global que consumen los filtros internos de cada componente (la pantalla Uso OpenAI filtra por `selectedClient().projectId`; el dashboard, el consumo de tokens y la lista de requerimientos filtran por `selectedClient().clientId`). `ClientContextService` (root, solo en memoria durante la sesión) guarda `clients` y `selectedClient` (el objeto `Client` completo: `clientId`, `name`, `projectId`, `active`, …; `null` = «Todos»), y expone `hasAssociatedClient`/`associatedClientId` (desde `AuthService.currentUser().clientId`), `selectableClients` (solo clientes activos, ordenados por nombre) y `selectedClientName`. `ShellComponent.ngOnInit` llama a `ensureLoaded()`, que pide `GET /api/clients` **una vez por usuario** (se recarga y descarta la selección si cambia el `userId`); `selectClient(id)` (o `null`) actualiza la selección y la **ignora** si el usuario tiene cliente asociado (su cliente queda fijado al cargar la lista). La cabecera del sidebar muestra un `<select>` nativo («Todos» + clientes activos) o, con cliente asociado, el nombre como texto. El `GET /api/clients` ya **no exige `clients.read`** (cualquier autenticado lista clientes para el filtro; el módulo `/clientes` sigue guardado por `clients.read` y las escrituras por `clients.write`).
- **Clientes** (feature folder `clients/`): the list (`ClientsListComponent`, route `/clientes`, guard `clients.read`) and the editor (`ClientFormComponent`, routes `/clientes/nuevo` and `/clientes/:id`, guard `clients.write`) talk to the backend `ClientsController` — `GET /api/clients`, `GET /api/clients/{id}`, `POST /api/clients` (201 + body), `PUT /api/clients/{id}` (204) and `DELETE /api/clients/{id}` (204, **borrado lógico**: the backend sets `deleted = 1`). Because those URLs start with `environment.apiBaseUrl` they go through `authInterceptor` (Bearer + 401 refresh). `services/clients.service.ts` maps the API's nullable camelCase payload onto a non-nullable `Client` (missing optionals → `''`) and sends empty optional fields as `null` (an empty email would fail the backend's `[EmailAddress]`; only `name` is required). `projectId` is edited and rendered in **plain text** (never masked). The list shows only **Nombre** and **Acciones** columns (búsqueda por nombre, filtro de estado con `all` por defecto, paginación de 10) and adds row actions **Editar / Activar-Desactivar / Eliminar** (native `confirm`), all shown only with `clients.write`; the form navigates back to `/clientes` with a `notice` in router state on success.
- Specs: `auth.service`/`auth.interceptor` tests must flush the extra `GET /api/auth/me/permissions` after login/refresh; component tests touching `*appHasPermission` seed permissions by injecting `PermissionsService` and setting its signals in `beforeEach`.

## Testing quirks

- Specs use Vitest globals (no Jasmine/Karma). `tsconfig.spec.json` sets `types: ["vitest/globals"]`.
- **Tokens dashboard tests**: `TokensDashboardComponent` now fires a second request (`GET /api/usage/costs`) in parallel with the tokens endpoint, so every test that triggers a load must flush **both** URLs (see the `flushTokens`/`flushCosts` helpers) or `httpTesting.verify()` fails. The specs also seed `PermissionsService` with `usage.read` in `beforeEach`: without that permission the component skips the costs request by design (`canReadUsage`).
- Dashboard tests use `provideHttpClientTesting()` + `HttpTestingController` to flush the API URL built from `environment.apiBaseUrl` and read/write `localStorage` (`veimen-web.hiddenStatuses` for the requirements dashboard). They clear `localStorage` in `beforeEach` and assert no outstanding requests in `afterEach`.
- **Known pre-existing issue**: `ng build` warns that the initial bundle exceeds the 500 kB budget (~760 kB before the token dashboard, ~840 kB after the usage dashboards). Not introduced by any single feature; the fix is lazy-loading routes or raising the budget in `angular.json`.
- **ngx-charts legends**: never use the built-in `[legend]="true"` with `legendPosition=Below`. `calculateViewDimensions()` only reserves _width_ for `LegendPosition.Right`, and `ChartComponent.update()` only splits the SVG when the legend is `Right` — with `Below` the `<svg>` keeps `height = view[1]` (the whole container) and the legend is rendered as a sibling _after_ it, so it overflows the card and overlaps whatever is below. Both charts that need a legend (the token dashboard's daily line and the uso-openai daily consumption line) render it as plain HTML next to the card title via `.mini-legend`.

- `public/TUCOOP_Gestion_de_Valor.pdf` is served as a static asset (the `assets` glob copies `public/**/*` to the output root), so it is referenced relative to `<base href="/">` as `TUCOOP_Gestion_de_Valor.pdf`. It is shown in an iframe by `business-model/BusinessModelComponent` (route `/business-model`), with a fallback link that opens it in a new tab.
- **The tab title of a top-level PDF navigation comes from the PDF's own `/Title` metadata**, not from the app: `window.open(url, 'name')`'s 2nd argument is the _window name_, not the visible tab title. `public/TUCOOP_Gestion_de_Valor.pdf` is a C2PA-signed document whose exported `/Title` was `(untitled)`, so it is set to "Modelos de Negocios" with `npm run pdf:set-title -- <archivo.pdf> "<titulo>"` (`scripts/set-pdf-title.mjs`). That script performs a PDF _incremental update_ (ISO 32000-1 §7.5.6): it only APPENDS a new `/Info` object + xref section + trailer with `/Prev`, so the signed byte range stays byte-identical and the C2PA credential is preserved. It inherits trailer entries through the `/Prev` chain (the C2PA revision's trailer omits `/Info`), is idempotent (bails on its own marker), and must be re-run if the PDF is ever re-exported.

## Conventions

- Prettier (`.prettierrc`): `printWidth: 100`, `singleQuote: true`, Angular parser for `*.html`. Prefer formatting before committing.
- Single quotes for JS/TS strings, 100-col width.
- **API date filters (`start_date`, `end_date`) are always sent in `YYYYMMDD` format (no dashes).** UI/components work with `YYYY-MM-DD` (native date inputs) and services convert with a private `toApiDate()` helper (`date.replaceAll('-', '')`) before building `HttpParams`. Any new service method that accepts a date range must follow this same convention.
- **Pagination bars are conditionally rendered**: show Anterior/Siguiente + page indicator only when more than one page exists (`totalPages() > 1`); with a single page (or no rows) the `.pagination` block is not rendered. This applies to every existing table with pagination (clientes, prompts, service-requests) and **must** be respected by any future table that adds pagination, so the buttons only appear when they are actually usable.
